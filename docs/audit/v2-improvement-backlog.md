# v2 Improvement Backlog — red-team of the go-forward plan

**Generated:** 2026-05-30 by a 64-agent workflow (`v2-improvement-redteam`).  
**Method:** 7 dimension reviewers (3 econometric, weighted) → 2 adversarial verifiers per critical/high finding → synthesis into a prioritized backlog.  
**Inputs read:** `docs/audit/v1/`, `docs/audit/v1-verified/`, `docs/plans/2026-05-11-v2-design.md`, `docs/plans/2026-05-11-phase1-implementation.md`, `RESUME.md`, and the v1 code.  
**Tally:** 42 findings raised · 37 survived verification · 5 refuted.

> This **builds on** the existing audit + verification reports — it does not replace them. It red-teams the *go-forward* v2 plan, not v1. Every finding was required to cite file:line / quoted text / a number; critical & high findings were then independently attacked by two skeptics, and any refutation downgraded the status.

---

## Executive summary

The backlog is led by reproducibility blockers that would prevent the MVP backtest from running at all: fridays_between() silently drops the 33 quarter-start vintages the DFM re-estimates parameters on, and Phase 2's flagship 'rebuild all 35 series from ALFRED' has no v1 fetcher for 32 of 35 series (only a 3-series patcher). Two sequencing fixes are nearly free but high-leverage: freeze the golden baseline from UNMODIFIED v1 before de-MATLAB (else it certifies the refactor against itself), and move the backtest runner from Phase 5 into Phase 3 so Phase 4's honest re-run is actually executable. The single highest-risk inference is the headline 'non-redundant but not significant' null, which is an underpowered failure-to-reject on T~=10-30 with zero power/MDE analysis — reframing sample size as the central narrative converts an indefensible null into the rigor signal both audiences want. On the methodology side, Phase 7a's mandatory 'COVID factor + outlier vector' is severed from the SV/Bayesian machinery that identifies it and gated only on a fragile 4-quarter RMSE target, so it should be re-specified as an identifiable outlier/dummy device with identification-aware exit criteria. Most remaining items are defensibility polish that make the deployed artifact honest: split the apples-vs-oranges six-model table by sample, pin a single terminal-week metric horizon, fingerprint the Spec in persistence, add a real-time-leak test, and pull the cheap GDPNow/ARMA benchmark forward (or unlist the deploy) so the public MVP is never a benchmark-less headline.

- **HLN small-sample correction does not fix the actual error (within-quarter pooling); it treats a symptom of a different problem** — `high` / partial · _Phase 4_
  - Claim: The plan's headline inference fix is 'quarterly-final-week DM with Harvey-Leybourne-Newbold (1997) small-sample correction' (v2-design §6, line 234; RESUME line 65). But HLN corrects DM for finite T given an ALREADY-correctly-specified long-run loss-differential variance; it is an adjustment to the DM denominator's degrees-of-freedom, multiplying by sqrt[(T+1-2h+h(h-1)/T)/T]. The verification (04_dm_weekly_granularity.md:138-141) shows that for a nowcast horizon h=1 and T≈30 this factor is ≈1, i.e. it does essentially NOTHING to the ex-2020 statistic. The real defect the verification identified is two-fold: (a) within-quarter pooling of ~19 serially-correlated weekly differentials (the sqrt(N/Q)≈4.38 inflation), and (b) absence of any long-run variance estimator. Once you move to one final-week observation per quarter (the plan's own 'quarterly-final-week' step), the pooling inflation is GONE — so HLN is being applied to a problem the granularity fix already solved, and HLN's own effect at h=1 is negligible. The plan markets HLN as THE correction when it is nearly a no-op here.
